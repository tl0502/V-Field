# P1 产品规则

确认日期：2026-09-11。来源：Native change `p1-product-rules-feasibility`。本文是可审阅的产品合同，不是业务已经实现的证明。

配套：[关键可行性](feasibility.md)、[整体重建规划](rebuild-plan.md)、[方向与边界](overview.md)。正式验收以该 change 的 brief、完整目标规格和 Runtime 为准。

## 交付边界

P1 交付角色、归属、权限、首期闭环、旧 UI 对照、概念实体和选型依据。不交付正式小程序、管理后台业务、云函数、业务数据库、物理表或旧库清理。

`experiments/p1-uniapp-probe/` 是标明为实验的可行性原型，不能当作 P2 正式基础。

## 核心角色

同一平台账号可以同时持有多个角色。验收允许测试账号兼任，合同上角色仍要分开。

| 角色 | 含义 | 首期最小能力 |
| --- | --- | --- |
| 访客 | 未登录 | 阅读已发布且有效的内容 |
| 平台账号用户 | 微信登录后的平台身份 | 申请加入业务域；不能凭登录直接发布 |
| 域成员 | 某业务域内已批准的成员 | 在该域发布内容 |
| 域运营者 | 经营某个业务域 | 批准或拒绝该域的入域申请 |
| 平台运营者 | 平台级治理身份 | 为预置汽车验证域指定域运营者 |

首位平台运营者由标明用途的初始化配置产生。不把「申请成为平台运营者」纳入首期。

## 内容归属与权限

- 用户可见内容必须同时有作者（平台账号）和所属业务域。
- 不允许无域的平台信息流，也不允许把业务域仅仅当成分类。
- 发布是域成员权限。登录用户必须先成为该域成员才能发布。
- 预置汽车验证域的入域方式是申请，并由该域运营者审批。未批准前不能发布。
- 未登录访客可以阅读已发布且有效内容的公开字段，不能阅读草稿或仅本人可见字段。
- 首期发布使用平台提供的汽车场景 Block（正文，以及可选的车源卡片）。不把「内容必须含车源项」写成平台规则。
- 真实发布和管理必须使用正式身份与授权，不能用开发令牌替代。头像文件校验不等于内容安全审核。

## 概念实体

只描述实体和归属，不冻结表名、字段、类型、索引或迁移。旧库表不是新版表设计。物理建表属于后续 P2 空数据环境。

| 实体 | 归属与关系 | 首期用途 |
| --- | --- | --- |
| 平台账号 | 由微信登录产生的唯一用户身份 | 申请、发布、管理端识别都指向它 |
| 微信身份 | 绑定到一个平台账号 | 小程序登录 |
| 业务域 | 独立于账号；预置汽车验证域是其中一例 | 内容与成员都挂在域上 |
| 域成员 | 平台账号 × 业务域 | 发布权的前提 |
| 入域申请 | 申请者账号 × 目标域，由域运营者处理 | 申请 → 批准/拒绝 |
| 内容 | 必须同时有作者账号和所属业务域 | 成员发布，访客阅读已发布内容 |
| 内容 Block | 平台提供，被内容使用 | 汽车场景正文与可选车源卡片 |
| 平台运营者资格 | 授予平台账号；首位来自初始化配置 | 指定域运营者 |
| 域运营者资格 | 授予平台账号，并绑定具体业务域 | 审批该域申请 |
| 管理凭证 | 绑定已有平台账号，不是另一套用户 | 管理网页用账号加管理密码登录 |

## 首期完整用户闭环

后续 P2/P3 要实现并验收的闭环是：

1. 平台运营者在平台级网页后台，为预置汽车验证域指定域运营者。
2. 用户在小程序微信登录，成为平台账号用户，并申请加入该域。
3. 域运营者在域级网页后台批准或拒绝申请。
4. 成为域成员后，用户发布一条同时绑定作者和该域的内容。
5. 访客在列表或详情阅读到该已发布内容。

完整资料、消息、关注、发现搜索、通用 Block 目录管理、完整成员治理、建域后台、支付和认证产品不纳入该闭环。汽车验证域作为预置场景存在。

本文件写清该闭环，不等于这些界面已经实现。

## 管理后台最小切片

首期纳入两套网页管理后台的最小切片，不是完整运营产品。旧 `apps/admin` 只是静态壳，没有可复用的管理业务界面；管理端按本合同新建。平台级与域级是两个网页入口。

| 后台 | 首期必须可验证 | 明确后置 |
| --- | --- | --- |
| 平台级网页后台 | 指定预置汽车验证域的域运营者 | 建域、平台运营者申请、审计、Block 目录 |
| 域级网页后台 | 批准或拒绝入域申请 | 完整成员治理、邀请体系、域配置大全 |

管理后台与小程序使用同一套平台账号。管理密码是管理端凭证，不创建第二套用户。

首期可验收的管理端登录是：平台账号 + 管理密码。网页微信扫码登录是同账号增强能力，依赖开放平台网站应用审核、开发者资质，以及与小程序绑定后的 UnionID；用户说明当前小程序没有企业申请。未验证不得写成已经开通。详见 [可行性](feasibility.md)。

## 旧 UI 对照

旧版实际小程序界面是用户端优先复用的设计基线。新版用户端用 uni-app 重做组件，不要求搬运旧 WXML，也不承诺逐像素一致。对照来源：旧项目 `apps/miniprogram/`，基线提交 `83b841f725c8b192ca87e8e07b05545a180a05cb`。

| 流程 | 旧入口 | 优先复用 | 必要适配及理由 |
| --- | --- | --- | --- |
| 浏览列表 | `pages/index/index`，自定义 tabBar 首页 | 顶栏、列表信息层级、自定义导航/tabBar 形态 | 域名称/切换接到真实业务域；分类、筛选、搜索在首期仍可标为未交付 |
| 阅读详情 | `pages/detail/detail` | 详情阅读布局与主要信息层级 | 展示作者和所属域；访客只看公开已发布内容。旧详情作者位是占位「发布者」 |
| 登录 | `pages/auth/index` | 登录页主交互 | uni-app 重做；使用真实微信登录，不用开发令牌 |
| 发布 | `pages/publish/publish` | 编辑、草稿到发布的主路径 | 发布前检查域成员；非成员引导申请；不强制必须有车源项。旧发布走开发令牌、不绑平台账号 |
| 我的/设置 | `pages/profile/*`、`pages/settings/*` | 资料与设置入口形态 | 可展示入域申请状态；完整资料、认证、徽章不是首期必过 |
| 发现/消息 | `pages/discovery/index`、`pages/messages/index` | 可保留 tab 入口 | 旧实现是占位；首期不把它们验收为已完成功能 |
| 他人主页 | `pages/user/index` | 公开资料阅读形态 | 随阅读闭环展示公开作者信息；旧页面缺少站内入口 |
| 平台管理 | `apps/admin` 静态壳 | 无业务 UI | 因必须指定域运营者而新建最小平台后台 |
| 域管理 | 无对应业务页 | 无 | 因入域审批必须可验证而新建最小域后台 |

因新权限、主题能力、uni-app 或微信限制而改变视觉方向、页面结构或主要交互时，必须在对应功能规格中说明依据。不批准任意改版。

微信用户端外观只跟随系统 / 微信 DarkMode。规划层仍记录浅色、深色、跟随系统三档，但不在微信端提供应用内强制浅色或深色作为无闪全局能力。详见 [可行性](feasibility.md)。

## 技术选型

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 用户端 | uni-app + Vue 3，只编译微信小程序 | 旧 UI 作为视觉与交互基线；不承诺 H5/App 用户端 |
| 管理端 | 两套独立网页 | 与小程序工程分开 |
| 服务端 | 自建 API + 独立数据库 | 旧 Node.js、PostgreSQL、S3 仅作候选，须按本合同核对后才能采用 |

本 change 不把上述选型落地为正式工程。

## 治理边界

任何真实发布或管理操作都需要正式身份、资源归属和授权。旧实现里的 `X-Dev-Token`、占位页和头像校验不能写成新版已完成的安全能力。完整内容审核、实名认证、官方标识审核和联系方式申请审批后置，但必须保持「未交付」而不是「已具备」。
