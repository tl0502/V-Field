# 新版方向与重建边界

方向确认日期：2026-09-10；整体规划确认日期：2026-09-11；P1 产品规则确认日期：2026-09-11。这里只记录用户已明确的方向与路线，阶段安排与功能恢复清单见 [整体重建规划](rebuild-plan.md)，已确认的角色、归属、首期闭环和选型见 [P1 产品规则](product-rules.md)，平台限制见 [关键可行性](feasibility.md)。具体验收由对应 Native change 管理。

## 产品方向

v域是跨行业的信息社区平台。平台提供通用能力，外部运营者经营不同业务域，内容可以使用平台提供的 Block。汽车是首个验证场景，整个项目不局限于汽车领域。

当前产品端方向是微信小程序。P1 已确认用户端使用 uni-app + Vue 3（只编译微信小程序），服务端使用自建 API 与独立数据库；旧 Node.js、PostgreSQL、S3 仅作候选。物理表结构不在 P1 冻结。

## 重建路线

- 采用独立新版、分阶段重建。
- 先评估整个项目的重建与复用边界、阶段依赖及首期目标，再确定具体开发任务。
- 旧版功能原则上全部保留，在新版逐项恢复；代码实现可以重写，旧业务细则需结合新目标核对，功能不因排期后置而自动取消。
- 用户认可旧 UI 设计，新版尽量复用旧布局、视觉样式、组件和主要交互；界面设计与底层代码分开判断，必要适配在对应功能中说明原因与方案。
- 旧代码、旧测试和旧文档是参考材料；保留价值需要结合新目标核对，已有测试通过不代表新版需求已经满足。
- 新版不迁移旧账号和业务数据，从空数据开始。用户已选择清空数据；实际旧数据库及存储清理尚未执行，待明确具体资源与范围后由独立执行任务承接。
- 旧项目源码保持独立，作为审查与复用参考；源码保留不代表要求保留旧业务数据。
- 每个真正进入实施的阶段通过 COMET Native 记录需求、完整目标规格、验收与归档。

## 已确认的体验需求

规划层仍记录「浅色／深色／跟随系统」三档。用户已确认：微信用户端只跟随系统 / 微信 DarkMode；应用内强制浅色或深色不作为微信端无闪全局能力。

用户报告旧版在 Android 真机与开发者工具中出现部分页面不变色、切页闪白、弹窗或键盘颜色不一致。以上属于用户报告与新版验收线索，不是已定位根因。P1 实验原型的微信 Dark Mode 人工视觉：用户判定开发者工具模拟器与真机均通过；iOS 未单独声明。微信端可用方案见 [可行性](feasibility.md)。不得把未跑检查写成已修复，也不得把实验原型写成正式工程。

主题需求不自动成为第一项业务开发任务。具体实施顺序由整体规划和后续用户流程的依赖确定。

## 事实与决定的边界

- 已确认的整体方向不等于所有旧产品细则都继续生效。
- 旧项目的 Node.js、PostgreSQL、S3、登录与车源实现仅作为候选技术和复用线索。
- 新工作区不继承旧项目的活动任务、已实现能力、验收结果、密钥或连接配置。
- 首期用户闭环、核心角色、内容归属、管理后台最小切片和技术选型已在 P1 确认，见 [产品规则](product-rules.md)。旧数据清理的具体资源仍未定位。物理表设计属于后续空数据环境，不在 P1 冻结。
- P1 规则交付不等于登录、发布、管理后台或数据库已经实现。

当前进度以 `comet.cmd status` 与 Native Runtime 为准，不在本概览维护另一套任务状态。
