# 独立新版重建规划

整体范围确认日期：2026-09-11。本文是 `plan-staged-rebuild` 的规划交付物，依据该 Native change 的 brief 和完整目标规格整理。规划交付与业务交付分别验收；各项功能的实际进度以对应 Native change 为准。

## 产品方向与工作区

v域是跨行业信息社区平台，由外部运营者经营不同业务域，内容可以使用平台提供的 Block。汽车是首个验证场景，不能用旧车源接口的限制替代平台规则。产品端方向是微信小程序。P1 已确认用户端使用 uni-app + Vue 3（只编译微信小程序），服务端使用自建 API 与独立数据库；旧 Node.js、PostgreSQL、S3 仅作候选。物理表结构在 P2 空数据环境中设计，不在本规划冻结。

| 工作区 | 用途与边界 |
| --- | --- |
| `D:\Project\WECHAT-PROJECT-next` | 独立新版，独立 Git 仓库和 COMET 状态，提供 Codex 与 Claude Code 入口 |
| `D:\Project\WECHAT-PROJECT` | 旧源码参考；当前规划不修改其文件、运行配置或数据库 |
| `D:\Project\开发流XXXXX` | 个人 COMET 模板，维护工作流模板与上游更新，不承载项目业务状态 |

用户已确认：旧版功能原则上全部保留，在新版分阶段逐项恢复；旧账号和业务数据不迁移，新版从空数据开始。规划层仍记录浅色、深色、跟随系统三档；微信用户端只跟随系统 DarkMode，不把应用内强制浅色/深色当作无闪全局能力。用户认可旧 UI 设计，新版尽量复用旧界面；代码实现和历史业务细则仍按新目标核对。

## 旧 UI 设计优先复用

旧版实际界面是新版优先复用的设计基线。能够沿用的页面布局、视觉样式、组件形态、信息层级和主要交互优先沿用，不因独立重建就默认重新设计整套 UI。

界面设计复用与代码复用分别判断：旧组件、样式和素材优先评估；底层状态、数据接口、鉴权或主题实现可以按新架构重写。复用 UI 不要求同时继承旧实现缺陷，也不把旧页面当作新业务规则的唯一依据。

P1 在明确核心角色和用户流程时，对照旧页面记录可复用的设计，以及因新业务目标、权限规则、主题能力或小程序实际限制而需要适配的地方。影响视觉方向、页面结构或主要交互的调整，应在对应功能规格中说明原因和方案后确认；本规划不批准任意改版，也不承诺未经核对的逐像素一致。

| F12 业务域、运营后台与通用 Block | 后台为静态壳，建域、成员、域角色及通用 Block 目录未成型 | 依据平台方向重建必要模型与运营流程；旧目录和页面不算已实现基础 | P1 明确规则，P2 最小权限基础，P3/P4 交付相关运营流程 |

治理与内容安全属于新平台发布和运营需要明确的共同约束：P1 确定适用边界，P3 在对应发布流程中落实必要检查，P4 完善运营处置。旧头像文件校验不等于完整内容审核，也不据此承诺未验证的微信接口能力。

后续核对旧源码发现遗漏功能时，补入本清单并关联相应 Native change。发现旧行为与新方向或隐私、安全要求冲突时，先记录差异和替代行为；功能取消或范围缩减需要在对应需求中明确确认，不能因实现困难或排期后置而默认删除。

## 重建与复用边界

平台、业务域、成员角色、资源归属、通用内容和 Block 的核心边界重新设计。登录、资料、编辑与阅读等旧功能保留目标，实现是否复用独立判断。

| 旧实现候选 | 可以核对的价值 | 新版采用前必须解决的差异与验证 |
| --- | --- | --- |
| 账号、会话与鉴权 | 身份关联、会话生命周期、本人和访客返回结构 | 对齐域角色、资源归属及失效规则；在新版验证真实身份链路，移除业务对开发令牌的依赖 |
| 加密与数据库访问 | 加密封装、数据访问接口、错误处理模式 | 核对新数据模型及运行环境，隔离配置与凭据；不复制旧库数据、连接信息或迁移历史作为新版基础 |
| 头像与 S3 适配 | 上传解析、文件校验、存储适配接口 | 核对媒体访问权限、存储边界及失败处理；用新版独立资源验证 |
| 编辑器、车源卡片与渲染 | 草稿交互、卡片表达和内容渲染经验 | 对齐通用内容、平台 Block、作者和业务域；不继承“内容必须有车源项”等汽车专用平台限制 |
| 页面基础、主题与导航 | 用户认可的旧布局、视觉样式、组件与主要交互，优先复用 | 区分设计与底层实现；核对共享状态、生命周期、首帧与原生界面能力，在目标设备重新验证 |

每次实际复用应在所属 change 记录：来源与版本、用途、新旧规则和接口差异、需要修改的部分、风险及新版验证方式。当前没有批准直接复制任何组件。旧测试通过只能作为调查线索，不能转记为新版通过；旧密钥、数据库连接和工作流运行状态不随代码复用。

## 分阶段交付

| 阶段 | 交付目标 | 进入条件 | 退出依据 |
| --- | --- | --- | --- |
| P0 整体规划 | 功能恢复清单、复用边界、空数据策略和阶段依赖 | 独立工作区和整体方向已确认 | 整体规划获确认，文档和工作区隔离通过独立验收 |
| P1 产品规则与关键可行性 | 明确角色、业务域、内容、归属、权限，建立用户流程与旧 UI 的对应关系，并核对关键平台限制 | P0 范围明确 | 核心约束有来源；旧 UI 的复用与必要适配有依据；技术风险有结论或明确边界，形成首期流程与选型依据 |
| P2 最小运行与权限基础 | 独立空数据环境、身份、资源归属、鉴权及基础交互能力 | P1 给出必要规则和选型依据 | 后续业务可以依赖真实身份和权限，不继续以临时开发身份替代正式授权 |
| P3 首个完整用户流程 | 围绕后续确认的首期用户目标组合必要能力 | 所依赖的身份、数据与平台基础可验证 | 用户能完整完成目标操作，失败反馈和权限边界也通过验收 |
| P4 其余功能恢复与运营扩展 | 逐项完成尚未交付的旧功能，并完善业务域运营及平台能力 | 已有完整流程形成可回查基线 | 每项有范围、兼容影响及验收证据；所有保留项均可追踪，未完成项继续登记 |

P1、P2 不要求先实现完整平台再验证业务价值；必要基础可以包含在第一个可验证用户流程内。任何真实发布或管理操作所需的身份、资源归属、权限和数据规则，都必须先完成或在同一流程中验证。探索原型标记为实验，不能算正式基础已完成。

P1 已确认首期完整用户闭环：平台运营者指定预置汽车域的域运营者 → 用户申请入域 → 域运营者审批 → 成员发布 → 访客阅读。主题仍是基础需求和可行性风险，不是该闭环的必过项。P2/P3 内部实现顺序按该闭环的依赖安排；后续阶段不因列在路线图中就自动成为活动任务。详细合同见 [产品规则](product-rules.md)。

## 空数据起步与旧数据清理

新版不迁移旧账号、会话或业务数据，从独立空数据环境开始；不要求旧账号标识、历史关系和业务记录保持连续。后续需要的最小配置和测试样例另行生成并注明用途，不将导入旧数据包装为初始化。

本路线不设置旧数据迁移、历史数据兼容或迁移切换里程碑。用户没有说明旧库只有测试数据，不据此推断旧数据性质。

用户清空旧数据的决定已经记录。实际执行另行定位部署环境、数据库及需要清理的存储资源，明确资源范围、操作方法和核验依据后再实施。本规划没有连接或清理旧库及存储，也没有建立新版业务数据库；旧源码继续保留作为参考。

## 主题与验证边界

规划层仍记录浅色、深色、跟随系统三档。微信用户端只跟随系统 DarkMode：原生窗口和 tabBar 走 `theme.json` 变量，业务样式走各页面/组件内的直接颜色 + `prefers-color-scheme`，不用 JS class 或 `setBackgroundColor` 涂色。后续验证覆盖跟随系统时的换色、系统浅切深闪色、切页首帧和导航背景，并分别确认弹窗、键盘、授权等原生界面的实际能力边界；不承诺以业务样式任意控制微信、操作系统或输入法界面，也不把应用内强制浅色/深色写成微信端无闪能力。

用户报告过 Android 真机及开发者工具中部分页面不变色、切页闪白、弹窗或键盘颜色不一致。这些是需求及验收线索，不是已定位根因。P1 实验原型的跟随系统视觉：用户判定开发者工具模拟器与真机均通过；iOS 未单独声明。旧版 Android 问题没有在本规划中写成已经复现或已经修复。

## 信息维护与后续任务

已确认方向见 [项目概览](overview.md)。本文保存整体规划；正式需求、验收和状态由 COMET Native 管理。修改整体范围时，通过相应 Native change 同步规划、概览和两端入口，避免各自维护相互矛盾的规则。

旧审查材料只在旧工作区或独立审查目录按需阅读，不加入新版主动检索范围。后续逐项恢复时核对旧源码事实和新用户目标，不让历史“已确认”标签替代当前决定。

P1 产品规则与关键可行性已形成，见 [产品规则](product-rules.md) 和 [可行性](feasibility.md)。后续 P2 建立空数据环境、真实身份、域归属和鉴权，并在那时设计物理表；P3 按已确认首期闭环组合可验证实现。实际旧数据清理仍由明确资源范围的独立任务承接。

每次实施选择可验证的用户结果，依次通过 Native 的需求确认、Build、独立 Verify 和 Archive。验收同时覆盖正常操作、错误与权限边界，以及相应设备和外部服务；无法验证的部分如实记录。只有具体范围包含可独立实现和验证的多个交付物时，才考虑 Supervisor 拆分。
