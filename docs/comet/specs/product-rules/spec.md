# P1 产品规则与关键可行性

本规格定义独立新版 P1 应交付的产品合同、旧 UI 对照、首期闭环、技术选型依据和平台限制结论。它不定义全部业务系统的最终实现，也不表示小程序或管理后台已经可运行。

## 目的

在 P0 整体规划之后，把平台/业务域的核心角色、内容归属和操作权限写成可执行合同；把首期用户闭环对照旧界面；核对会改变设计的微信与 uni-app 限制；给出后续 P2/P3 可以依赖的选型依据。

## Requirements

### Requirement: 交付边界

本 change 交付规则文档、可行性结论，以及为核对平台限制而明确标记的实验原型。不交付正式小程序工程、云函数、业务数据库、旧数据清理或完整运营产品。

实验原型不能当作 P2 正式基础。规划交付与业务交付分别验收。

#### Scenario: 正确解释 P1 完成

- GIVEN P1 产物已经可以审阅。
- WHEN 用户查看工作区、规则文档和进度。
- THEN 能区分规则/可行性已交付与业务尚未实现；若存在实验原型，它被标明为实验；不会发现未经确认就完成的登录、发布、管理后台或数据库迁移任务。

### Requirement: 核心角色

合同上至少区分下列角色。同一平台账号可以同时持有多个角色；验收允许测试账号兼任，但不能把多个角色合并成一个角色。

| 角色 | 含义 | 首期最小能力 |
| --- | --- | --- |
| 访客 | 未登录 | 阅读已发布且有效的内容 |
| 平台账号用户 | 微信登录后的平台身份 | 申请加入业务域；不能凭登录直接发布 |
| 域成员 | 某业务域内已批准的成员 | 在该域发布内容 |
| 域运营者 | 经营某个业务域 | 批准或拒绝该域的入域申请 |
| 平台运营者 | 平台级治理身份 | 为预置汽车验证域指定域运营者 |

首位平台运营者由标明用途的初始化配置产生。不把「申请成为平台运营者」或完整建域后台纳入首期。

#### Scenario: 角色不能互相替代

- GIVEN 读者审阅 P1 角色合同。
- WHEN 对照首期闭环中的指定运营者、申请、审批、发布和阅读。
- THEN 每个步骤都对应明确角色；登录用户、域成员、域运营者和平台运营者没有被写成同一个身份。

### Requirement: 概念数据合同

P1 必须写出首期闭环用到的实体及其归属关系，作为后续建库的依据，而不是数据库表设计。

| 实体 | 归属与关系 | 首期用途 |
| --- | --- | --- |
| 平台账号 | 由微信登录产生的唯一用户身份 | 申请、发布、管理端识别都指向它 |
| 微信身份 | 绑定到一个平台账号 | 小程序登录 |
| 业务域 | 独立于账号；预置汽车验证域是其中一例 | 内容与成员都挂在域上 |
| 域成员 | 平台账号 × 业务域 | 发布权的前提 |
| 入域申请 | 申请者账号 × 目标域，由域运营者处理 | 申请 → 批准/拒绝 |
| 内容 | 必须同时有作者账号和所属业务域 | 成员发布，访客阅读已发布内容 |
| 内容 Block | 平台提供，被内容使用 | 汽车场景正文与可选车源卡片 |
| 平台运营者资格 | 授予平台账号；首位来自初始化配置 | 指定域运营者 |
| 域运营者资格 | 授予平台账号，并绑定具体业务域 | 审批该域申请 |
| 管理凭证 | 绑定已有平台账号，不是另一套用户 | 管理网页用账号加管理密码登录 |

不在本阶段冻结表名、字段、类型、索引或迁移。旧库表结构不是新版表设计。

#### Scenario: 实体合同不升级成表结构

- GIVEN 读者查看 P1 的数据合同。
- WHEN 核对其详细程度。
- THEN 能看到上述实体和归属关系，并且没有把 CREATE TABLE、字段类型或迁移脚本写成已经批准的数据库设计。

### Requirement: 内容归属与权限

用户可见内容必须同时有作者和所属业务域。不允许无域的平台信息流，也不允许把业务域仅仅当成分类。

发布是域成员权限。登录用户必须先成为该域成员才能发布。预置汽车验证域的入域方式是申请，并由该域运营者审批。未登录访客可以阅读已发布且有效的内容，不能阅读草稿或仅本人可见字段。

首期发布使用平台提供的汽车场景 Block（正文，以及可选的车源卡片）。不把「内容必须含车源项」写成平台规则。不得用开发令牌替代正式身份和域授权。

#### Scenario: 内容同时具备作者和业务域

- GIVEN 一条用户可见内容出现在规则示例或合同中。
- WHEN 检查它的归属。
- THEN 同时存在作者和所属业务域；没有把无域内容或「域只是筛选」写成正式模型。

#### Scenario: 发布前必须是域成员

- GIVEN 一个已登录但不是某域成员的用户。
- WHEN 核对该域的发布权限。
- THEN 合同要求先申请并获域运营者批准；未批准前不能发布。

#### Scenario: 访客可以阅读已发布内容

- GIVEN 一条已发布且有效的汽车验证域内容。
- WHEN 未登录访客打开列表或详情。
- THEN 合同允许阅读公开字段；草稿和仅本人字段保持不可见。

### Requirement: 首期完整用户闭环

可验证的首期闭环是：

1. 平台运营者在平台级网页后台，为预置汽车验证域指定域运营者。
2. 用户在小程序微信登录，成为平台账号用户，并申请加入该域。
3. 域运营者在域级网页后台批准或拒绝申请。
4. 成为域成员后，用户发布一条同时绑定作者和该域的内容。
5. 访客在列表或详情阅读到该已发布内容。

完整资料、消息、关注、发现搜索、通用 Block 目录管理和完整成员治理不纳入该闭环。汽车验证域作为预置场景存在，首期不要求运营者从零建域。

#### Scenario: 首期闭环步骤完整

- GIVEN 读者按 P1 产物走查首期目标。
- WHEN 从指定运营者到访客阅读。
- THEN 能看到上述五步及所需权限；主题专项、完整资料或消息关注没有被写成该闭环的必过项。

### Requirement: 管理后台最小切片

首期纳入两套网页管理后台的最小切片，不是完整运营产品。

| 后台 | 首期必须可验证的能力 | 明确后置 |
| --- | --- | --- |
| 平台级网页后台 | 指定预置汽车验证域的域运营者 | 建域、平台运营者申请、审计、Block 目录 |
| 域级网页后台 | 批准或拒绝入域申请 | 完整成员治理、邀请体系、域配置大全 |

旧 `apps/admin` 只是静态壳，没有可复用的管理业务界面。管理端按本规格新建，并在对照表中记录「无旧业务 UI」的依据。平台级与域级是两个网页入口。

管理后台与小程序使用同一套平台账号。管理密码是管理端凭证，不创建第二套用户。

网页微信扫码登录是同账号的增强能力，不是首期唯一可验收路径。官方前置条件包括：在微信开放平台注册、拥有已审核通过的网站应用、开通微信登录；若要与小程序识别为同一用户，还需开放平台开发者资质认证并绑定同主体小程序以使用 UnionID。用户说明当前小程序没有企业申请。本 change 必须核对这些限制并记录结论；未验证不得写成已经开通。

因此首期可验收的管理端登录是：平台账号 + 管理密码。若网页微信登录经验证可用，可作为增强，不改变身份模型。

#### Scenario: 两套后台只要求最小切片

- GIVEN 读者查看管理后台范围。
- WHEN 核对待交付能力和后置项。
- THEN 平台级至少能指定汽车域运营者，域级至少能审批入域申请；完整运营产品没有被写成首期必交付。

#### Scenario: 管理端登录有可验收退路

- GIVEN 用户没有企业资质，网页微信登录能力未证实。
- WHEN 阅读管理端登录合同。
- THEN 首期可验收路径是同一平台账号加管理密码；扫码登录被列为待验证增强能力，并写明开放平台/UnionID/个人主体限制。

### Requirement: 旧 UI 对照与必要适配

旧版实际小程序界面是用户端优先复用的设计基线。新版用户端用 uni-app 重做组件，不要求搬运旧 WXML。管理端无旧业务界面可复用。

| 流程 | 旧入口 | 优先复用 | 必要适配及理由 |
| --- | --- | --- | --- |
| 浏览列表 | `pages/index/index`，自定义 tabBar 首页 | 顶栏、列表信息层级、自定义导航/tabBar 形态 | 域名称/切换接到真实业务域；分类、筛选、搜索在首期仍可标为未交付，不能当功能完成 |
| 阅读详情 | `pages/detail/detail` | 详情阅读布局与主要信息层级 | 展示作者和所属域；访客只看公开已发布内容 |
| 登录 | `pages/auth/index` | 登录页主交互 | uni-app 重做；使用真实微信登录，不用开发令牌 |
| 发布 | `pages/publish/publish` | 编辑、草稿到发布的主路径 | 发布前检查域成员；非成员引导申请；不强制必须有车源项 |
| 我的/设置 | `pages/profile/*`、`pages/settings/*` | 资料与设置入口形态 | 可展示入域申请状态；完整资料、认证、徽章不是首期必过 |
| 发现/消息 | `pages/discovery/index`、`pages/messages/index` | 可保留 tab 入口 | 旧实现含占位；首期不把它们验收为已完成功能 |
| 他人主页 | `pages/user/index` | 公开资料阅读形态 | 随阅读闭环需要展示公开作者信息；联系方式申请仍后置 |
| 平台管理 | `apps/admin` 静态壳 | 无业务 UI | 因首期必须指定域运营者而新建最小平台后台 |
| 域管理 | 旧项目无对应业务页 | 无 | 因入域审批必须可验证而新建最小域后台 |

因新权限、主题能力、uni-app 或微信限制而改变视觉方向、页面结构或主要交互时，必须在对应功能规格中说明依据。不批准任意改版，也不承诺逐像素一致。

#### Scenario: 对照表区分复用与新建

- GIVEN 读者查看流程与旧页面对照。
- WHEN 检查用户端和管理端。
- THEN 用户端列出优先复用的旧布局/交互，以及入域、归属、主题或平台限制导致的适配；管理端标明旧后台无业务界面、属于必要新建。

### Requirement: 技术选型依据

产品端是微信小程序，使用 uni-app 与 Vue 3。本阶段不承诺 H5 或 App 用户端。

服务端与数据使用自建 API 和独立数据库。旧 Node.js、PostgreSQL、S3 兼容存储仅作候选，必须按本规格的身份、域隔离和配置隔离核对后才能采用。本 change 不建库、不部署。

管理端为独立网页，与小程序工程分开。

#### Scenario: 选型被写清且不假装已经落地

- GIVEN 读者查看技术选型。
- WHEN 核对本 change 的工作区。
- THEN 能看到 uni-app 用户端、自建 API 与独立数据库、两套管理网页的依据；同时能看出它们尚未作为正式业务工程落地。

### Requirement: 平台限制与可行性核对

规划层仍记录浅色、深色、跟随系统三档。用户已确认微信用户端只跟随系统 DarkMode；应用内强制浅色或深色不作为微信端无闪全局能力。本 change 在微信开发者工具中，针对 uni-app 产物做最小核对，至少覆盖：

- 跟随系统时，应用可控制界面的换色
- 原生窗口 / 原生 tabBar 的 `theme.json` 变量，以及业务样式的 `prefers-color-scheme`
- 系统由浅切深、切页首帧背景
- 授权弹窗、键盘等原生界面的实际可控边界

真机复现旧主题问题、iOS 测试不是 P1 完成条件。用户报告过 Android 真机与开发者工具不一致，根因仍未在本 change 证实。系统浅切深是否还闪，以人工结果为准，未跑不得写成已消除。

个人主体小程序不能微信认证，也不能申请微信支付；服务类目也与非个人主体不同。这些是已知平台限制，不在本 change 扩展为首期支付或认证产品。

网页微信登录与 UnionID 打通按上一节核对，结论必须区分「文档所述前置条件」和「本账号已开通」。

#### Scenario: 主题与原生界面限制有边界

- GIVEN P1 可行性结论已经写入。
- WHEN 读者查看主题和原生界面。
- THEN 规划层三档需求仍被记录；微信端合同是跟随系统，强制浅色/深色没有被写成微信端无闪能力；应用可控区域与微信/系统/输入法控制区域被区分；未跑的真机、iOS 或系统浅切深检查没有被写成通过。

#### Scenario: 个人主体限制不被夸大或忽略

- GIVEN 用户说明当前小程序没有企业申请。
- WHEN 阅读可行性结论。
- THEN 个人主体在认证、支付、开放平台绑定等方面的限制被记录为已知风险或已核对事实；没有把未开通能力写成已经可用，也没有把整个产品端判为不可做。

### Requirement: 治理与内容安全边界

任何真实发布或管理操作都需要正式身份、资源归属和授权，不能继续使用开发令牌作为生产授权。头像文件校验不等于内容安全审核。完整内容审核、认证、官方标识审核和联系方式申请审批后置到对应业务 change，但 P1 必须把它们登记为未交付，而不是已具备。

#### Scenario: 安全缺口保持显式

- GIVEN 读者查看治理边界。
- WHEN 对照发布和管理操作。
- THEN 合同要求正式授权；开发令牌和头像校验没有被写成完整安全能力。
