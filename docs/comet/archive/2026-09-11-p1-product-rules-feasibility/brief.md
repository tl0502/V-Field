# Outcome

为 v域新版给出可审阅的 P1 产品规则与关键可行性结论：明确核心角色、业务域、内容归属和操作权限；把核心用户流程对照旧 UI；核对会改变设计的微信小程序限制；据此确定首期完整用户闭环和技术选型依据。

用户原始请求：「恢复进度，comet」，并选择立即开始 P1。本 change 交付规则与可行性，不代表业务小程序或数据库已经实现。

# Scope

- 在独立新版工作区 `D:\Project\WECHAT-PROJECT-next` 产出 P1 正式规则与可行性文档，并同步已确认结论到项目概览/整体规划中需要保持一致的部分。
- 定义平台与业务域的核心角色、内容归属、资源授权和必要的治理边界；汽车是首个验证场景，不把汽车专用限制写成平台规则。
- 将核心用户流程对照旧小程序实际页面（首页、发现、消息、我的、登录、发布、详情、资料/设置等），记录可复用的布局、视觉、组件和主要交互，以及因新规则、三档主题或平台限制必须适配之处。
- 核对会改变设计的关键平台限制，至少覆盖：微信端跟随系统 DarkMode、自定义导航与 tabBar、切页首帧背景、系统浅切深闪色、授权弹窗/键盘等原生界面的可控边界。本 change 用微信开发者工具、在 uni-app 产物上做最小核对；真机复现旧主题问题和 iOS 测试不是完成本阶段的条件。
- 确认首期完整用户闭环，以及支撑该闭环的技术选型依据；该闭环的业务实现由后续 P2/P3 承接。
- 写出首期所需的概念实体与归属关系（平台账号、业务域、成员、入域申请、内容、管理凭证）。不冻结表名、字段、类型或迁移脚本；物理建表在后续空数据环境中设计。
- 旧项目 `D:\Project\WECHAT-PROJECT` 仅作只读对照；本 change 不修改旧仓库、不连接旧库、不复制密钥。

# Non-goals

- 不实现登录、主题切换、发布、阅读、资料、后台等业务功能，不创建正式小程序工程、云函数或业务数据库，不冻结物理表结构或编写迁移。允许为平台限制核对建立明确标记的实验原型，该原型不能当作 P2 正式基础。

- 不把旧车源专用限制（例如内容必须含车源项、发布走开发令牌）升级为新平台规则。
- 不在本 change 交付完整运营后台、关注/消息闭环、通用 Block 目录管理或内容安全审核产品。
- 不因独立重建默认重做整套 UI，也不承诺未经核对的逐像素一致。
- 不预先创建覆盖 P2–P4 的 Supervisor 子任务。

# Decisions

- 已确认（P0）：独立新版、跨行业平台、外部运营业务域、平台 Block、汽车首个验证场景、旧功能保留、旧 UI 优先复用、空数据起步、主题三档。
- 已确认（本轮）：启动 P1 Native change `p1-product-rules-feasibility`，隔离方式为当前目录 `main`。
- 已确认（范围）：本 change 交付产品规则与可行性结论，不交付业务实现；旧数据清理仍由后续独立任务承接。
- 已确认 Q1：小程序侧目标仍是「登录用户在汽车验证场景发布一条已归属内容并被阅读」。配合 Q7/Q8 后，可验证的首期闭环为：平台运营者指定预置汽车域的域运营者 → 用户申请入域 → 域运营者审批 → 成员发布 → 访客阅读。完整资料、消息关注、完整运营治理不纳入该闭环。
- 已确认 Q2：用户可见内容必须同时有作者和所属业务域；不允许把无域平台信息流或「域只是分类」当作正式内容模型。
- 已确认 Q3：本 change 用微信开发者工具做最小核对；真机复现旧主题问题、iOS 测试不是 P1 完成条件。
- 已确认（用户补充）：产品端前端框架使用 uni-app。P1 仍只以微信小程序为产品端；H5/App 不在本阶段承诺。旧 UI 作为视觉与交互基线，在 uni-app 中重做组件，不要求搬运旧 WXML。
- 已确认 Q4：服务端与数据走自建 API + 独立数据库。旧 Node/PostgreSQL/S3 仅作候选，需按新合同核对后才能采用；本 change 不建库、不部署。
- 实现选择：uni-app 侧使用 Vue 3。不因此改变已确认的页面结构或交互目标。
- 实现选择：汽车验证域在首期作为预置场景存在，不把建域后台纳入首期闭环。
- 实现选择：P1 使用普通 Native change，不预先拆 Supervisor；若确认后的交付物出现可独立验收的多个结果，再在最终确认前检测拆分。
- 已确认 Q5：发布是域成员权限，不是登录后的全局能力。登录用户必须先成为该域成员才能发布。
- 已确认 Q6：未登录访客可以阅读已发布且有效的内容；看不到草稿和仅本人可见字段。
- 已确认 Q7：成为预置汽车验证域成员的方式是申请，并由域运营者审批。
- 已确认 Q8：首期纳入两套网页管理后台的最小切片，不是完整运营产品。平台级至少能指定预置汽车域的域运营者；域级至少能批准或拒绝入域申请。旧后台无可用业务界面，管理端按新合同新建，并在规格中说明依据。
- 实现选择：小程序产品端用 uni-app + Vue 3；管理端是两套独立网页，不把 H5/App 用户端纳入本阶段。
- 实现选择：空数据起步下，首位平台运营者由标明用途的初始化配置产生；不把「申请成为平台运营者」纳入首期。同一平台账号可以同时持有多个角色，验收可用测试账号兼任，但合同上平台运营者、域运营者、域成员仍是不同角色。
- 已确认 Q9：管理后台与小程序使用同一套平台账号。网页微信扫码登录是期望能力，但当前小程序无企业资质，该能力必须在本 change 核对。用户确认的首期可验收退路是「平台账号 + 管理密码」，管理密码是管理端凭证，不创建第二套用户体系。
- 拆分检测：本 change 交付一份相互关联的规则与可行性结论，可行性实验服务于同一份合同，不拆为 Supervisor；小程序、平台后台、域后台的业务实现由后续 change 承接。
- 已确认（数据合同深度）：P1 只写实体与归属，不锁表结构。物理表在后续 P2 建立空数据环境和权限基础时设计并验收。
- 已确认（微信主题 B）：微信用户端只跟随系统 / 微信 DarkMode。应用内强制浅色或深色不作为微信端无闪全局能力。规划层三档需求仍记录；微信端实现走官方 `darkmode` + `theme.json` + `prefers-color-scheme`，不用 JS 在 `onThemeChange` 后刷窗口色。系统由浅切深是否还闪，以人工结果为准。
- 已确认（人工视觉 2026-09-11）：用户判定实验原型在开发者工具模拟器与真机均通过 CHECKLIST；未另报单向不能换色。iOS 未单独声明。旧 Android 主题问题未写成已复现或已修复。真机复现旧问题、iOS 测试仍不是 P1 完成条件。
