# Outcome

为 v域建立可审阅、可分阶段执行的独立新版重建规划。规划说明全部旧功能如何逐项恢复、哪些边界需要重建、哪些旧实现可作为复用候选、阶段之间有什么依赖，以及后续业务 change 如何进入实施与验收。

用户原始请求：「独立新版分阶段重建」。这是路线选择；本 change 交付整体规划，不代表全部业务系统已经重建。

# Scope

- 新工作区为 `D:\Project\WECHAT-PROJECT-next`，使用独立 Git 仓库和本地 COMET 模板，提供 Codex 与 Claude Code 两端入口。
- 保留跨行业平台、外部运营业务域、平台提供 Block、汽车首个验证场景的整体方向。
- 输出完整功能恢复清单、候选复用边界、阶段依赖、空数据初始化与旧数据清理边界，以及后续需求拆分原则。
- 纳入已确认的三档主题需求与 Android/开发工具体验反馈，但不把主题自动指定为第一项业务任务。
- 旧版功能原则上全部保留，在新版分阶段逐项恢复；旧 UI 设计已获用户认可，尽量复用其布局、视觉和主要交互；代码实现及历史业务细则分别核对。
- 用户已决定「不迁移，清空数据」：新版账号和业务数据从空开始，不安排旧数据迁移；实际旧库及存储清理由后续明确目标的操作承接。
- 首期具体用户闭环、技术栈细选、每个模块的业务细则，在整体范围形成后按相应 Native change 确认；此阶段不替用户冻结这些决定。

# Non-goals

- 本 change 不实现主题、登录、编辑器、后台或其他业务模块，也不创建承诺覆盖全部平台实现的 Supervisor 子任务。
- 不复制旧应用、旧密钥、旧数据库连接或旧 Runtime 状态；不执行旧库迁移、清理或对外发布。
- 不把「尽量复用旧 UI」解释为必须复制旧代码或继承旧缺陷；不默认重新设计整套旧界面，也不擅自从恢复清单删去旧功能。
- 不把旧测试结果、历史原型或未经复现的用户报告当成新版验收通过。
- 不在此次规划中冻结所有业务细则、具体技术栈或首个业务实现任务。

# Acceptance examples

- A1: 新版工作区有独立 Git 根和可用的 Codex/Claude Code COMET 接入；旧项目的 Git HEAD、既有改动状态和核对文件内容保持原样。
- A2: 用户可以通过一份完整规划判断主要模块的重建与候选复用边界、阶段依赖、三档主题需求和后续需确认的业务问题；不存在把旧实现或候选建议写成已批准新版规则的情况。
- A3: 规划验收完成后只代表规划交付；工作区和状态不会显示主题、账号或其他业务实现已经完成，后续实施由各自的 Native change 承接。
- A4: 规划明确新版不迁移旧账号和业务数据、从空数据开始；不安排迁移里程碑，不把用户决定推断为旧库只有测试数据；旧数据清理的目标与执行证据尚未形成时，不报告已经清理。
- A5: 旧功能清单覆盖原实现审查中的功能组，逐项区分已实现、部分实现与占位，给出恢复目标、阶段候选和验收关注点；功能原则上全部保留，阶段后置不等于删除，任何范围例外须在对应需求中明确确认。
- A6: 规划、概览和双平台入口明确旧 UI 设计优先复用，区分布局/视觉/主要交互与底层代码；P1 对照用户流程记录旧页面的复用与必要适配，影响设计的调整有依据和确认边界，不能默认整套改版。

# Constraints and invariants

- 旧项目源码保留为参考；当前规划不改写旧环境，新版不连接旧库。用户已选择空数据起步，旧账号、会话和业务记录不作为新版连续性约束。
- 旧数据库和存储的实际清理须先定位具体环境与资源边界，再在相应执行任务中完成并核验；当前没有执行清理，也没有承诺永久保留旧业务数据。
- 旧功能保留原则与旧实现复用分开记录；不因为某项复杂、存在旧缺陷或未列入首期，就默认为取消。
- 所有候选复用都需要核对新模型与接口边界，并在新版重新验证；不整体复制旧车源模型来代表通用内容平台。
- 旧 UI 设计以用户认可的现有界面为优先基线；架构重写不等于视觉改版，必要的界面调整要说明与新目标或平台限制的关系。
- 功能、阶段和任务状态各有明确含义：阶段建议不是已批准业务需求，也不是已经运行的子任务。
- 主题三档是已确认要求，但主题优先实施不是已确认决定；原生界面能力边界需后续按目标设备验证。
- 当前只确认 Android/开发工具的用户反馈，iOS 仍为未测试；不承诺无法验证的原生界面控制能力。
- Runtime 状态与验证报告由 COMET 管理；本 brief 与完整目标 Spec 保存正式需求，项目概览和两端入口只同步已经确认的项目边界。
