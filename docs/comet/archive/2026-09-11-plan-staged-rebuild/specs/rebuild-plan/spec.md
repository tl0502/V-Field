# 独立新版整体重建规划

本规格定义整体重建规划应覆盖的内容与边界，不定义全部业务系统的最终实现。用户已确定新版不迁移旧数据、从空数据开始，并原则上保留全部旧功能、逐项恢复。整体规划已于 2026-09-11 获用户确认，交付及验收状态以 Runtime 为准。

## 目的

在独立新版中，先建立跨行业平台的整体模块边界、功能恢复清单、依赖关系、数据处理边界和阶段交付方法，再按确认结果逐段实施。功能恢复与实现复用分别判断，符合新边界的旧组件可在审查和新版验证后采用。

## Requirements

### Requirement: 独立工作区与旧项目保护

新版使用独立 Git 仓库和 COMET 状态。旧项目仅作参考与回退依据，初始化和规划不得改写其文件、Git 状态、数据库或运行配置。新版初始化仅包含协作工具、已确认的新方向和正式规划产物。

#### Scenario: 检查新版初始化的隔离范围

- GIVEN 独立新版工作区已经建立。
- WHEN 核对两个工作区的 Git 根、当前状态和新版文件清单。
- THEN 两个 Git 根不同，旧项目既有状态保持原样，新版没有导入旧应用源码、环境密钥或旧工作流执行状态。

### Requirement: 产品方向与模块边界

规划以跨行业信息社区平台为目标，区分平台、业务域、通用内容、平台 Block 与首个汽车验证场景。旧功能原则上全部保留，在新版逐项恢复；用户认可旧 UI 设计，尽量复用其布局、视觉与主要交互。代码实现和历史细则仍按新目标核对。下列内容给出规划边界，不把目录存在或旧功能已写过当成新版已完成：

| 模块或能力 | 初步重建判断 | 必须确认或验证的边界 |
| --- | --- | --- |
| 平台、业务域与内容归属 | 重新设计核心边界 | 一项业务行为作用于哪个域、由谁拥有、如何被授权 |
| 账号、会话与服务端鉴权 | 保留功能，按新权限模型重建；旧代码为复用候选 | 身份、域角色、资源归属和开发令牌的边界统一 |
| 通用内容与 Block | 重新设计通用模型 | 汽车作为业务扩展场景，不把必须存在车源项写成平台规则 |
| 发布、编辑、阅读 | 保留旧功能，按新交互目标重建或拆分 | 先明确数据和权限合同，再决定编辑器形式与复杂度 |
| 页面基础、主题、导航与输入 | 优先复用用户认可的旧 UI，底层基础能力按新架构评估 | 设计复用与代码复用分开；共享状态、生命周期、首帧背景、原生界面限制及目标设备表现 |
| 个人资料、联系方式、徽章与认证 | 保留功能方向，区分现有可用能力与未完成流程，逐项恢复或补齐 | 隐私告知与最终行为一致；挂载上限、可见规则、认证流程等细则另行确认 |
| 发现、消息、关注与搜索 | 保留旧版功能入口所代表的目标，分阶段定义并完成闭环 | 已实现能力、部分实现和占位分别登记；不能用占位页通过功能验收 |
| 治理与内容安全 | 根据新平台的发布与运营边界明确必要范围 | 旧版未完成的能力不写成已经可用，相关约束在对应业务上线前落实 |
| 平台后台与域运营 | 按最终运营闭环安排 | 管理权限、建域与运营范围不能由旧静态后台壳推导 |
| 加密、数据库访问、S3 适配等技术组件 | 可审查的复用候选 | 接口隔离、配置安全、兼容性与新版验证均满足后才采用 |

#### Scenario: 审查每个模块的去向

- GIVEN 用户已确定旧功能原则上全部保留、分阶段恢复。
- WHEN 审查最终模块清单。
- THEN 每个模块都有明确的功能目标、重建或候选复用边界、阶段位置及理由；旧功能不会因后置而从范围消失，旧测试通过、旧文档标签和旧页面布局不会代替新版验收。

### Requirement: 旧 UI 设计优先复用

旧版实际界面是新版优先复用的设计基线。能够沿用的页面布局、视觉样式、组件形态、信息层级和主要交互优先沿用，不因为独立重建而默认重新设计整套 UI。旧组件、样式和素材优先评估；数据、状态、鉴权和主题等底层代码仍可按新架构重写并重新验证。

P1 在梳理核心角色和用户流程时，对照旧页面记录设计复用与必要适配。因新业务目标、权限规则、三档主题或小程序实际限制而需要改变视觉方向、页面结构或主要交互时，在对应功能规格中说明原因和方案后确认。本规划不批准任意改版，也不承诺未经核对的逐像素一致。

#### Scenario: 将认可的旧 UI 作为设计基线

- GIVEN 用户明确认可旧 UI 设计，并要求新版尽量复用。
- WHEN 审阅整体规划、概览、双平台入口及 P1 的交付范围。
- THEN 旧布局、视觉和主要交互被列为优先复用基线，UI 设计与底层实现分开判断；用户流程需要对照旧页面，必要适配有依据及确认边界，不会把独立重建解释为默认整套视觉改版。

### Requirement: 功能恢复与差异清单

下表依据旧项目实现审查建立恢复范围线索；代码事实仍属于旧版，新版各项均尚未实现。它保留功能目标，不把表内旧字段、数量限制、具体接口和未完成流程直接确认为新版细则。P2/P3/P4 是阶段候选，最终排期由对应闭环确认；未进入首期的功能继续留在恢复清单。

| 功能组 | 旧版核对事实 | 新版恢复目标 | 阶段候选与验收关注点 |
| --- | --- | --- | --- |
| 登录、账号与会话 | 有微信登录、协议版本记录、会话读取和注销；外部服务未在旧审查中实测 | 恢复账号进入、会话与退出闭环，账号重新产生 | P2；真实身份、会话失效、协议告知与资源权限一致 |
| 个人资料与设置 | 有公开用户号、昵称、头像、简介、本人页、公开页及设置入口 | 恢复资料维护与本人/他人查看能力 | P2 最小资料，P3/P4 补齐；编辑、保存、展示与隐私边界可验证 |
| 手机号与资料联系方式 | 有微信取号/自填路径及多种联系类型，支持隐藏、公开、锁定 | 保留相关功能目标，在新规则下恢复获取、维护和可见控制 | P3/P4；核验状态、公开确认、本人/访客权限及告知一致 |
| 联系方式查看申请 | 后端有待审申请，界面仍提示未开发，缺审批与放行闭环 | 保留申请目标，后续确认并补齐完整交互与授权规则 | P4；不能仅凭创建申请或占位按钮宣称完成 |
| 徽章、身份认证与官方标识 | 有徽章目录、授予记录与挂载；认证和官方标识有入口但无完整审核链路 | 恢复徽章展示与配置能力，分别定义授予和认证的完整规则 | P3/P4；展示权限、授予来源与审核结果可追溯 |
| 内容编辑与汽车场景 | 有正文 Delta、草稿/车源卡片编辑、标签、有效期、发布去重 | 保留编辑和车源表达能力，接入通用内容与平台 Block 边界 | P3/P4；作者/域归属、草稿到发布、重复提交与渲染完整可验证 |
| 内容列表与详情 | 有有效车源列表与详情；尚无已发布内容更新/删除接口 | 恢复阅读能力，发布后的生命周期规则另行设计 | P3；正确展示、访问权限、有效状态和失败情形可验证 |
| 首页、发现与导航 | 首页有列表，分类、推荐/最新、域切换及搜索含占位 | 保留相关入口目标，逐项明确真实可用的浏览与发现行为 | P3/P4；占位展示与已交付功能分别登记 |
| 消息、关注与粉丝 | 有页面和计数占位，没有完整关系与业务接口 | 保留功能目标，按新平台交互规则形成闭环 | P4；真实关系、消息来源及权限可核验，不能用固定计数验收 |
| 主题与基础体验 | 用户报告旧主题不一致；新版三档选择已确认 | 统一浅色、深色、跟随系统的应用体验和切换行为 | P1 验证关键限制，P2 建基础，后续页面持续验收；不预定其为首个任务 |
| 上传与媒体 | 有头像上传及 S3 兼容适配，通用内容媒体链路未完整实现 | 恢复头像上传；内容所需媒体能力随对应闭环定义 | P2/P3/P4 按依赖；访问、错误处理与配置隔离在新版验证 |
| 业务域、运营后台与通用 Block | 后台为静态壳，缺完整建域、成员、域角色及通用 Block 目录 | 依据已确认平台方向重新建立必要模型与运营流程 | P1 定义边界，P2 最小权限基础，P3/P4 完成相关闭环 |

后续盘点发现的旧功能必须补入清单，不能因本表按功能组归纳而遗漏。发现旧行为与新平台边界或隐私、安全要求不一致时，在相应功能的 Shape 中列出差异与替代行为；涉及功能取消或范围缩减的例外必须明确确认，不能把重写实现解释为自动获准删减功能。

#### Scenario: 追踪旧功能是否被完整保留

- GIVEN 旧功能原则上全部保留，且旧实现中同时存在可用功能、部分实现和占位。
- WHEN 将旧实现审查与规划中的恢复清单逐组对照。
- THEN 每组都有恢复目标、旧版完成度和阶段候选；后置项仍在范围中，旧数量限制和接口不被自动固定，未完成链路也不被写成新版已交付；发现遗漏后补入清单。

### Requirement: 阶段依赖与任务选择

规划应给出按依赖组织的阶段，而非仅按页面名称列任务。以下为整体阶段分组，组内顺序与具体第一条业务任务尚未确定：

| 阶段 | 目标 | 进入条件 | 退出依据 |
| --- | --- | --- | --- |
| P0 整体重建规划 | 明确保留旧功能的恢复清单、复用边界、空数据策略及阶段依赖 | 独立工作区和新方向已确认 | 用户能够审阅并确认整体规划 |
| P1 产品合同与关键可行性 | 明确核心角色、域、内容、权限边界，将核心用户流程与旧 UI 对照，并验证会改变设计的平台限制 | P0 的功能范围原则明确 | 核心约束有来源；旧 UI 复用与必要适配有依据；技术风险有结论或明确边界，不预定首个界面实现 |
| P2 最小运行与权限基础 | 建立独立空数据环境、身份、资源归属、鉴权与基础交互能力 | P1 给出必要合同与选型依据 | 后续业务可依赖这些能力，不需要继续用临时开发身份替代正式权限 |
| P3 首个完整交付闭环 | 按后续确认的首期用户目标，组合所需能力形成端到端结果 | 所需身份、数据与平台基础已验证 | 对应用户可以完整完成目标操作，错误与权限边界也能验证 |
| P4 其余功能恢复与运营扩展 | 完成恢复清单中尚未交付的旧功能，并建设所需域运营及平台扩展 | 已有闭环形成可回查基线 | 每次交付有独立范围与验收证据；清单覆盖全部保留项，未完成项不因排期后置而消失 |

阶段之间按已验证的能力推进，必要基础可与首个闭环一起交付，不要求先建成所有通用平台模块才验证业务价值。新版从空数据开始，不增加旧数据迁移与切换里程碑；实际旧数据清理单独明确目标和核验方式。具体首期用户闭环和 P1/P2 内的实施顺序在后续相应 change 中确认。

#### Scenario: 检查阶段依赖是否尊重基础约束

- GIVEN 规划已经列出阶段目标。
- WHEN 沿依赖关系检查任何真实发布或管理操作。
- THEN 身份、资源归属、权限和数据合同位于相应业务操作之前或同一可验证闭环之内；探索原型被明确标记，不被当作已经完成的正式基础。

#### Scenario: 单项痛点不自动决定项目顺序

- GIVEN 已确认三档主题需求与旧版主题体验问题。
- WHEN 审查阶段规划和第一项业务任务的决定来源。
- THEN 主题作为基础需求和风险存在，不能仅因该痛点已被描述就宣布它是第一项业务任务；实际任务选择具有整体范围与用户目标依据。

### Requirement: 信息与复用边界

新版按已确认的新方向与正式规格实施。旧资料留在旧工作区或独立审查目录，按需核对。复用结论要记录用途、新旧合同差异、需要改动的部分及新版验证方式；不将旧代码整体搬入后再把它当成新需求。

#### Scenario: 判断一个旧模块是否可以复用

- GIVEN 有一个旧技术组件或业务模块被列为候选。
- WHEN 决定采用该候选。
- THEN 记录其与新边界的适配和风险，并在新版重新验证；没有把旧环境凭据、历史工作流状态或旧通过结果当作复用的组成部分。

### Requirement: 空数据起步与清理边界

用户已决定「不迁移，清空数据」。新版不继承旧账号、会话或业务数据，从独立空数据环境开始；后续需要的最小配置与测试样例另行生成并明确用途，不能将导入旧数据包装为初始化。旧功能保留不要求旧记录、账号标识或历史关系保持连续。

规划不设置旧数据迁移、历史数据兼容或切换核对里程碑。用户的回答没有说明旧数据是否属于真实用户数据，不得将其改写为「旧版只有测试数据」。

用户清理旧数据的意图已经记录；执行前仍需定位实际数据库、部署环境及需要清理的存储资源和边界，具体动作由后续执行任务承接。当前 change 不连接旧库、不执行删除；旧源码继续保留为参考，源码保留和数据保留是不同事项。

#### Scenario: 区分空数据起步的决定与清理执行

- GIVEN 用户明确选择不迁移并清空数据。
- WHEN 审阅新版数据策略和当前执行状态。
- THEN 规划明确旧账号和业务数据不迁入新版、新版从空数据开始；没有迁移里程碑，也没有把旧库的数据性质当作已知事实；实际清理在目标和核验记录形成前保持未执行，不报告已经清空。

### Requirement: 体验需求与验证边界

新版应将浅色、深色、跟随系统三档作为需求。规划记录用户报告的页面漏切换、切页闪白、弹窗/键盘颜色不一致，以及 Android 真机、开发工具已报告问题而 iOS 未测试的证据边界。

正式主题方案需要区分应用控制的业务界面与微信、操作系统、输入法控制的界面；本规划不冻结渲染引擎或实现方法，也不承诺任意原生界面换肤能力。

#### Scenario: 区分需求、用户报告与实际验证

- GIVEN 用户确认了主题三档并描述了旧版体验问题。
- WHEN 阅读规划中的主题范围与验证计划。
- THEN 三档需求被保留，根因与原生控制能力没有被假定为已证实，iOS 也没有被计为已验证通过。

### Requirement: 后续交付规则

当前 change 只交付整体规划。后续每个实施阶段应选择一个可验证结果，通过 Native 的需求确认、实现、检查、独立验收和归档推进。仅当具体范围确实包含可独立实现和验证的交付物时，才考虑 Supervisor，不因路线图有多个阶段就预先创建全部子任务。

#### Scenario: 正确解释当前阶段的完成

- GIVEN 整体规划后续通过验收。
- WHEN 用户查看当前产物与进度。
- THEN 能区分规划已交付与业务尚未实现，且不会发现未经确认就已经执行的主题、登录、编辑器或数据库迁移任务。

## 确认边界与后续决定

数据策略、功能范围原则及完整 Shape 均已明确确认，本整体规划无待回答的阻塞问题。当前交付物是一份统一规划，恢复清单与阶段依赖需整体一致，不创建 Supervisor 子任务；交付及验收状态由 Runtime 维护。

首期具体用户闭环、技术栈、各模块业务细则、旧数据清理的实际资源与执行方式，在对应后续 change 中确认。确认本规划不等于这些业务实现已获逐项批准，也不等于系统已经重建完成。
